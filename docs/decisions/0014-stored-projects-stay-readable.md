# 0014: Stored projects stay readable: snapshot shape versions, upgrades, and release migrations

Status: Accepted (October 2026)

## Context
Projects store their generated snapshot (`ARCHITECTURE.md`, project snapshots), so a plan never changes underneath it when a template changes (0008). The first M3 design kept only the current schemas: once a template changed the shape of what it stores, older snapshots could not be read until regenerated, which would replace their numbers. The owner asked that old designs keep working, and that migrations and backfills run as part of every release rather than by hand.

## Decision
- **Two version numbers per template.** `version` (0008) changes when the output for the same parameters changes, whether a number or anything else stored with it, such as a source added to the structural working (owner's decision, October 2026, #36). `snapshotVersion` changes when the shape of the stored snapshot changes: fields added, removed, renamed, or restructured, including parameters and structural inputs. Each snapshot records both.
- **Upgrades, one per shape step.** A template's `snapshotUpgrades[n]` turns a shape-n snapshot into shape n + 1. Reading a snapshot applies the upgrades in order, then parses it with the current schemas. Upgrades only restructure what is stored; they never call the template to recompute. A field that older versions did not produce is optional in the new shape, or derived from data the snapshot already holds. So an old plan keeps exactly the numbers it was made with, and the version report (0008) still shows what regenerating would change. This holds for parameters and structural inputs too (#429): stored parameters are read with a relaxed schema, so a new parameter stays missing from an older plan rather than being made up, and is filled as a suggestion with its basis only when the owner edits or regenerates; a structural input filled this way is an unconfirmed suggestion (#417). A test applies every upgrade to the fixtures and fails on any value it writes there that the plan did not hold, other than renames and facts listed per template.
- **Fixtures that are never rewritten.** Each template commits `snapshots/v<n>.json` for every template version: its worked examples as that version stored them, so every shape version has at least one fixture. Tests read every fixture through the upgrades, check the current fixture reads back exactly, and compare freshly generated snapshots with the current fixture, with numbers within `sameNumber` (below). Changing a template's output without a new template version and a new fixture fails `pnpm check`, and so does changing what it stores without a new shape version and an upgrade. Every fixture, the current version's included, is pinned by a hash of its content, recorded by the script that writes it (#431). Hashes are only added: CI also compares the hash file with the base's, a pull request's base branch or the commit main pointed to before a push, and fails when an entry other than `shown/` was changed or removed, or when a `shown/` entry changed without a new version's fixture (#705). Each fixture holds one snapshot per worked example (owner's decision, October 2026, #215: a fixture per template version, so the comparison never lapses). Fixture sizes are in Fixture sizes below.
- **What a plan shows is pinned too (#431).** Core derives a plan's tables, build steps and drawings from its stored outputs on every read, so the promise covers generic code as well as stored numbers. The current version's fixture keeps a copy of what its plans show, `shown/v<n>.json`: the template's `plan` and `steps`, the build steps with no tools and with a fixed small shop's tools, and the dimension text of every drawing. It is written with the fixture, pinned by hash, and replaced at the next version. Changing how a stored plan reads, such as the precision of a saw setting, fails `pnpm check` until each template it changes has a new version and fixture.
- **What the sweep generates is pinned too (#706).** Four worked examples per template leave most parameters unreached, such as a burial depth of 0 or other hanger mounts. Each template's seeded sweep (`templates/sweep.ts`) already generates hundreds of parameter sets, so the current version also keeps `sweeps/v<n>.json`: the sweep's seed and count and, for each draw the schemas accept, what it generated (the plan's outputs, or the issues that refused it) in a compact form. The form is the draw's distinct numbers, rounded to 7 decimal places, and a hash of its JSON with each number replaced by its place in that list, so every string, key, and number's position is pinned. Storing every number would take 0.9 to 2.3 MB per template version; this takes about 300 KB, as much as a fixture. The template's `sweep.test.ts` compares the sweep it already runs with that digest, numbers within `sameNumber`, so changing a template's output for any swept draw fails `pnpm check` until the template has a new version. The tolerance is twenty times the rounding, so rounding cannot flip a comparison. The digest is written with the fixture by `write-snapshot-fixture`, which replaces the previous version's, and its hash lives in the same hash file as a `sweeps/` entry under the same rule as `shown/`: CI fails if it changes without a new version's fixture.
- **Stored and fresh output are compared within a tolerance (owner's decision, November 5, 2026, #706).** Every test that compares stored output with freshly generated output, and the version report (0008), uses `diff` in `snapshot/diff.ts`: numbers count as the same within `sameNumber`, 1e-6 plus 1e-12 of the larger value, and everything else compares exactly. ECMAScript defines `Math.sin`, `cos`, `tan`, `atan`, `log`, `pow` and the like as implementation-approximated, so their last bits may differ between platforms. They do: run on macOS arm64, Linux arm64, and Linux x64 (CI's runner), 200,000 inputs gave the same results only for `+ - * /`, `sqrt`, `hypot`, and `cbrt`. The swing set's sweep then differed in 7 draws between the Mac and Linux x64, by amounts like 13.437500000000002 against 13.4375. Last-bit differences are near 1e-15 of a value; a sixty-fourth of an inch is 0.0156. Stored values and computation stay exact (hard rule 4); only the comparison allows for this.
- **A release step.** `pnpm db:migrate` (`apps/api/scripts/release.ts`) checks that the new code can read every stored snapshot and that each project's template ID is its snapshot's, then applies the committed Drizzle migrations. Vercel runs it in every production build of the API service; preview builds skip it. It uses Neon's direct connection (`DATABASE_URL_UNPOOLED`) when set. If any stored snapshot cannot be read, it fails the build before migrating or writing anything, so code that cannot read existing projects does not go live and the database is left as the previous deploy knows it. Snapshots are not rewritten into the new shape at release (changed October 2026, #201): the previous deploy keeps serving until the new one is promoted and would report rewritten snapshots as `newer-snapshot`. A snapshot stays in the shape it was saved in until it is saved again, and reads upgrade it.
- **Migrations are compatible with the code still running.** The release runs before the new code serves requests, so a migration must not break the previous deploy: add before using, and remove only what the previous deploy no longer reads.
- Parameters and structural inputs live only in the snapshot, so upgrades keep one copy current. The `projects` columns that duplicated them are dropped (migration 0001).

## Consequences
- Upgrades accumulate. They are small pure functions over JSON with a fixture each, which is cheaper than losing old plans.
- Stored snapshots can be in any older shape, so no upgrade can be removed while a row might still be in its shape. The fixtures already require keeping them.
- The release runs in this order, holding a Postgres advisory lock so overlapping builds take turns: a read-only check of every stored snapshot, the migrations, then backfills of derived data such as history rows. A backfill reads each row under a row lock and writes only if nothing changed it meanwhile, so a save made during a build wins.
- A production build needs database access. If the release fails, the deploy fails and the previous deploy keeps serving an unchanged database.
- A migration that drops, renames, retypes, adds a NOT NULL constraint, or adds a check, unique, foreign key, or primary key constraint or a unique index fails a test unless a comment on the line just before it says why stored rows and the previous deploy's writes still satisfy it (`apps/api/test/migrations.test.ts`). Migration 0005 broke the previous deploy's tool saves this way before the test existed. Another test applies every migration but the last, stores every snapshot fixture, then applies the last, so a constraint that existing projects break fails `pnpm check` before it reaches the release step.
- Changing a template's sweep (its sampler, seed, or count) changes its digest, so it needs a new template version, as adding a worked example does.
- A value that lands exactly halfway between two sixteenths could display differently on two platforms, since display rounds the exact value. That is rare, and harmless today because production runs on one kind of machine. Fixtures and `shown/` are also compared within the tolerance, so they pass on any platform.
- A read-time change still reaches older plans: only the current version's copy of what plans show is kept, because keeping one per version would forbid any change to generic display code. A pull request that changes it says that older plans read differently. Build steps for other tool inventories and drawing geometry other than dimension text are not pinned.
- Rolling back code past a shape change leaves snapshots in a newer shape than the old code reads. It reports them as `newer-snapshot` instead of guessing; roll forward instead.

## Fixture sizes, November 5, 2026 (#708)

The owner's decision in #215 expected about 350 KB per fixture. Measured at 760b84c:

| Files | Count | Size |
|---|---|---|
| `snapshots/`, swing set | 40 | 187 to 463 KB |
| `snapshots/`, record cabinet | 23 | 225 to 417 KB |
| `snapshots/`, workbench | 2 | 935 and 937 KB |
| `shown/`, one per template | 3 | 1.5 MB (swing set), 4.1 MB (record cabinet), 14.4 MB (workbench) |
| `sweeps/`, one per template | 3 | 284 to 339 KB |

Snapshot fixtures add about 0.4 MB per swing set or record cabinet version and 0.9 MB per workbench version. `shown/` holds every drawing's dimension text, so it is the largest; it is replaced at each version, not added to. `contract.test.ts` caps each file's size by kind, about a quarter over today's largest (1.2 MB for `snapshots/`, 18 MB for `shown/`, 450 KB for `sweeps/`), so a file that outgrows its cap fails `pnpm check` and the cap is raised on purpose, in review.

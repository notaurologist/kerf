# 0014: Stored projects stay readable: snapshot shape versions, upgrades, and release migrations

Status: Accepted (October 2026)

## Context
Projects store their generated snapshot (`ARCHITECTURE.md`, project snapshots), so a plan never changes underneath it when a template changes (0008). The first M3 design kept only the current schemas: once a template changed the shape of what it stores, older snapshots could not be read until regenerated, which would replace their numbers. The owner asked that old designs keep working, and that migrations and backfills run as part of every release rather than by hand.

## Decision
- **Two version numbers per template.** `version` (0008) changes when the output for the same parameters changes, whether a number or anything else stored with it, such as a source added to the structural working (owner's decision, October 2026, #36). `snapshotVersion` changes when the shape of the stored snapshot changes: fields added, removed, renamed, or restructured, including parameters and structural inputs. Each snapshot records both.
- **Upgrades, one per shape step.** A template's `snapshotUpgrades[n]` turns a shape-n snapshot into shape n + 1. Reading a snapshot applies the upgrades in order, then parses it with the current schemas. Upgrades only restructure what is stored; they never call the template to recompute. A field that older versions did not produce is optional in the new shape, or derived from data the snapshot already holds. So an old plan keeps exactly the numbers it was made with, and the version report (0008) still shows what regenerating would change.
- **Fixtures that are never rewritten.** Each template commits `snapshots/v<n>.json` for every shape version: its worked examples as stored in that shape. Tests read every fixture through the upgrades, check the current fixture reads back exactly, and compare the shape of freshly generated snapshots with the current fixture. Changing what a template stores without a new shape version, an upgrade, and a new fixture fails `pnpm check`. Every fixture before the current shape is pinned by a hash of its content, each fixture holds one snapshot per worked example, and while the template version matches the current fixture's, the worked examples must regenerate it exactly.
- **A release step.** `pnpm db:migrate` (`apps/api/scripts/release.ts`) checks that the new code can read every stored snapshot, then applies the committed Drizzle migrations. Vercel runs it in every production build of the API service; preview builds skip it. It uses Neon's direct connection (`DATABASE_URL_UNPOOLED`) when set. If any stored snapshot cannot be read, it fails the build before migrating or writing anything, so code that cannot read existing projects does not go live and the database is left as the previous deploy knows it. Snapshots are not rewritten into the new shape at release (changed October 2026, #201): the previous deploy keeps serving until the new one is promoted and would report rewritten snapshots as `newer-snapshot`. A snapshot stays in the shape it was saved in until it is saved again, and reads upgrade it.
- **Migrations are compatible with the code still running.** The release runs before the new code serves requests, so a migration must not break the previous deploy: add before using, and remove only what the previous deploy no longer reads.
- Parameters and structural inputs live only in the snapshot, so upgrades keep one copy current. The `projects` columns that duplicated them are dropped (migration 0001).

## Consequences
- Upgrades accumulate. They are small pure functions over JSON with a fixture each, which is cheaper than losing old plans.
- Stored snapshots can be in any older shape, so no upgrade can be removed while a row might still be in its shape. The fixtures already require keeping them.
- The release runs in this order, holding a Postgres advisory lock so overlapping builds take turns: a read-only check of every stored snapshot, the migrations, then backfills of derived data such as history rows. A backfill reads each row under a row lock and writes only if nothing changed it meanwhile, so a save made during a build wins.
- A production build needs database access. If the release fails, the deploy fails and the previous deploy keeps serving an unchanged database.
- A migration that drops, renames, retypes, or adds a NOT NULL constraint fails a test unless a comment beside it says why the previous deploy no longer depends on what it changes (`apps/api/test/migrations.test.ts`). Migration 0005 broke the previous deploy's tool saves this way before the test existed.
- Rolling back code past a shape change leaves snapshots in a newer shape than the old code reads. It reports them as `newer-snapshot` instead of guessing; roll forward instead.

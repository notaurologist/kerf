# Milestones

Status: Draft v0.1

Target: plans ready to build the swing set from. No date set yet.

Each milestone is small enough to break into agent tasks and leaves something that works and is checked. A milestone is done when every acceptance criterion passes, `pnpm check` is green, and any docs it affects are updated.

Geometry and structural math come before any UI because they decide the success criteria (`PRODUCT.md`): no recuts from wrong numbers, one trip to the store.

---

## M0: Repository setup

- pnpm workspace with `apps/api`, `apps/web`, `packages/core` (0002).
- TypeScript strict, Biome, and Vitest configured at the root; `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm check`, and `pnpm dev` work across all packages.
- Exact versions pinned, Node 24 in `.nvmrc` and `engines`. Installed versions recorded in a new decision record.
- Pre-push hook and GitHub Actions run `pnpm check` (0010).
- `AGENTS.md` commands section matches reality.

**Accept when:** a fresh clone runs `pnpm install && pnpm check && pnpm dev` with no errors, and CI passes on a pull request.

## M1: Units and swing-set geometry

- `units/`: fractions to 1/16 inch, feet-inches display, the angle convention and the matching angle to the board's edge (`DOMAIN.md`, Units).
- Swing-set template (0008): parameter schema with ranges, validation of contradictory combinations, and generation of parts, hardware, operations, placements, and site layout.
- Cut list and shopping list in `outputs/`, with board grouping that allows for kerf and end trim.

**Accept when:** hand-checked worked examples (at least a typical adult-capable configuration and an edge-of-range one) match the template output; fit tests pass (legs land on the footprint, leg tops meet the beam at the joinery positions, brace ends meet the legs); every displayed length rounds through one formatter; contradictory parameters produce clear validation issues.

## M2: Structural checks

- NDS design values and adjustment factors for the species and grades the owner is likely to buy, stored as sourced data (0009). Values and formulas checked against the current NDS edition before entry.
- Generic checks in `structural/`: beam bending, shear, and deflection for any point loads between two supports, built-up members, and hardware margin (`DOMAIN.md`, Structural checks). No template-specific code.
- The swing-set template's structural model: swing load, per-hanger load, load cases, service conditions, and its checklist items (`DOMAIN.md`, Swing set specifics, Loads).
- Missing inputs produce "input needed," never a default.

**Accept when:** each check matches a hand-calculated worked example, including the symmetric hand-check cases and an asymmetric load layout; every result lists inputs, formula, adjustment factors, assumptions, and source; no copy says "safe" or "pass."

## M3: API, database, login, and first deploy

- Drizzle schema and migrations for tools, projects, project history, sessions, and login attempts.
- Login per 0007: password-hash script, session middleware on every route, rate limiting.
- Tool inventory and project routes (`ARCHITECTURE.md`); project snapshots generated by core and stored.
- Vercel and Neon set up (0006), free-tier limits re-checked and recorded, migrations run, secrets in Vercel only.

**Accept when:** route tests on PGlite cover every route without a session, login rate limiting, and a snapshot round trip; the deployed API accepts a login and stores a project; reading a project whose template version is behind reports the difference.

## M4: Web app: projects, cut list, shopping list, structural review

- Login screen, tool inventory editor, project list with status.
- Project editor with validation from core's schemas; structural inputs entered with no defaults.
- Cut list, shopping list, structural checks with expandable working, and confirmation checklist, all rendered from the snapshot.
- Notice when the template version is behind, with an explicit regenerate action.

**Accept when:** the owner can create the swing-set project on the laptop and see the same cut list, shopping list, and structural review on a phone; every length and angle on screen comes from core's formatters.

## Design: information architecture, visual design, and design system

A phase, not a single task. It starts from the wireframes and data requirements in #39 and ends with a design system the rest of the app is built from (`PRODUCT.md`, principle 6). Each stage explores several directions, critiques them against principles of good design, and records the choice and its reasons before the next stage builds on it.

1. **Information architecture.** What lives where, and how I move between planning on the laptop, shopping on the phone, and building in the garage.
2. **Layout and grid.** The spatial system for phone, tablet, laptop, and print.
3. **Typography.** Typefaces, scale, and how numbers, fractions, and angles are set, since numbers are most of the content.
4. **Color.** A palette with defined roles (text, surfaces, flags, margins, diagram ink), in light and dark.
5. **Diagram language.** Line weights, dimension and angle labels, hatching, and clearance zones, consistent with the rest of the system.
5a. **Number entry and form states.** How lengths and angles are typed and echoed back, and the states of every form (#67).
5b. **Words.** A content guide for method text, flags, errors, and labels (#68).
6. **Design system.** Tokens, components, and usage guidance built in code, with the M4 screens rebuilt on it.
7. **A repeatable garage check.** A written protocol for checking the design on a phone in the garage, on the laptop, and in print, run once on the system's screens and again in M7 (#69).

**Accept when:** I'm proud of the key screens, checked on a real phone in the garage, on the laptop, and on a printed page; each stage's decision is recorded; and every M4 screen is built from the design system. "It works" is not the bar.

## M5: Diagrams

- Isometric assembled view, exploded view, per-part cut details with angles and reference faces, and the site layout with clearance zones, from core's 2D primitives (0004), drawn in the diagram language from the Design phase.
- Print styles: each diagram and the cut list print on their own pages.

**Accept when:** projection functions have unit tests; the diagrams for the M1 worked examples are checked by eye against hand sketches; diagrams are readable on a phone and print cleanly.

## M6: Knowledge base and build steps

- Tool types, skills, expert-check categories, and methods for every operation the swing set needs, written for the owner's tools plus one alternative per operation (`PRODUCT.md`, MVP feature 6). Safety-relevant entries sourced.
- Build steps: ordered steps, method selection from the inventory, flags, and generic tool suggestions.
- Project history rows written when a snapshot is saved.

**Accept when:** knowledge-base tests pass (every entry parses, every reference resolves); changing the inventory changes the chosen methods as expected; every step in a known risk category shows its flag.

## M7: Shop use and the build

- Phone and tablet layout for build steps, one step at a time, large text, built from the design system.
- Review the plans with an experienced builder; record changes as issues.
- Build the swing set.

**Accept when:** the swing set is built from the app's plans with no recuts from wrong numbers and one trip to the store, or every miss is recorded as an issue with its cause.

## M8: Starting points

After the MVP. Starting a project today means about 30 empty fields and no output until Create.

- Start from a template's worked example or an earlier project, with a preview of the output before saving (#98).
- Each template carries the dimensions its project type conventionally uses, as data, and asks a few questions only for what it can't determine on its own (the space, who uses it, a style choice). The answers become suggested parameters from template code, each labeled with its source, convention, or rule of thumb (#163).
- Structural inputs are never suggested. Answers that are structural inputs, such as a rider's weight, are entered by the user (hard rule 3).

**Accept when:** the swing set can be started from a worked example, an earlier project, or its questions, each opening a filled form with a preview; hand-checked worked examples cover the questions' suggestions, including a yard too shallow for the conventional beam height; and no structural input is filled in except from the owner's own answers or project.

The new-project screen

The new-project and edit screens share one layout: the form, with the preview beside it (#98 added the preview to the new-project screen). The form has 33 fields for the swing set. This page shows what is wrong with that layout today, draws three directions for it, and asks two smaller questions: how the fields are grouped, and how one field is laid out. Then it recommends one of each.

Measured October 30, 2026 in a local copy, starting from the spec's worked example. Laptop frames are 900 px wide; on a phone, scroll them sideways inside their box. Values and counts in the sketches are the form's, started from the spec's worked example: 33 fields, 14 of them input needed and the project name empty.

What is there now

Laptop, 1366 pxThe form is the narrow side of the layout (24rem, about 370 px), one field per row, so the page is about 5,500 to 5,800 px tall. The preview takes the other 60% of the width, but it stays at the top of the page: after the first screen the right half is empty. It says nothing until every dimension and hardware entry can be read, and the hardware is never filled in for you, so with a worked example it stays empty until the last section is done.
Tablet, 768 pxThe preview drops below the form, and the form's sections become two-column grids. This is where the issue's alignment problems show: help text of one to three lines puts inputs in the same row at different heights (Ground slope and Burial depth), "in per ft" wraps to two lines and makes Ground slope's input narrower than Burial depth's, and sections end with a lone field (Seat height).
Phone, 375 pxOne column, about 6,000 px tall. Inputs with a unit are narrower than those without.
Everywhere"Input needed" sits beside a short label and on its own line under a long one. Create is only at the bottom. Beam stock is in Lumber under Dimensions and hardware; beam species and grade is in Beam lumber under Structural inputs, a long scroll away.

What stays the same in every direction

  • Core describes the form as data and checks it; the screen renders any template's form (hard rule 6). Errors show only after Create or Save, through the error summary (#67).
  • Structural inputs and confirmed hardware are never filled in for you (hard rule 3). An empty one says "Input needed".
  • The preview is the API's dry run (#56, #98), labeled "Preview, not saved".
  • The edit screen uses the same layout, so a change here changes both.

N1

One column of fields, with the preview and Create always in view

The form becomes the wide side at a readable width; the preview becomes a side column that stays in view as you scroll (position: sticky). At its top: how much is left and the Create button. Every field is one row, so nothing has to line up across a row. Below about 60rem the preview follows the form, and Create is also in the screen's header.

For
One column is what NN/g recommends for forms ("Present fields in a single column layout"), and it removes the row-alignment problems at every width rather than fixing them. The preview is visible next to whichever field you are on, as on the edit screen today. Create and the count of what is left are always reachable (issue items 1, 2, 3, 5, 7). The smallest change: the same components, with a sticky side and a progress line.
Against
The page is still long (one field per row); grouping by part (question 2) shortens the jumps but not the length. A sticky column taller than the screen has to scroll on its own, so the preview gets its own scroll inside the side.

N2

A list of groups, one group at a time

GOV.UK's task list: the groups down the left with a status each ("Entered", "2 input needed"), one group's fields in the middle, the preview on the right. Create sits under the list. On a phone the list is its own screen and each group opens from it.

N3

Groups you open and close, with the preview in view

Every group on one page as a disclosure whose summary says how much is left ("Beam · 2 input needed"). Groups with something left open by themselves; finished ones close. The preview stays in view beside them, as in N1.

Two questions inside the direction

2. How the fields are grouped

G1 As now

Dimensions and hardware (Frame, Lumber, Site, Swings, Hardware), then Structural inputs (Beam lumber, Loads, Limits and ratings). Nothing changes in core.

G2 By part of the project Recommended

Beam (length, height, stock, plies, species and grade, incised, moisture, ply bolts, deflection limit), Legs, Crossbars, Gussets, Site, Swings (with the hanger rating), Loads. Structural inputs keep "Input needed" on each field and the line saying none is filled in for you moves to the top of the form. The grouping is data in the template's folder (principle 6); the generic form code only renders it. The plan's Parameters and inputs reads the same groups. No change to outputs, so no template version bump.

Issue item 6. NN/g: split a form's fields into sections by topic. A woodworker thinks of the beam as one thing: what size, what board, what species.

3. How one field is laid out

F1 A fixed shape for every field Recommended

Label; "Input needed" always on its own line under the label; the hint; then the input at a fixed width by kind (numbers and lengths 10rem, choices up to 20rem, as GOV.UK sizes inputs to their expected length), with the unit after it in a slot that never wraps (GOV.UK: suffixes outside the input, the label or hint still naming the unit). The echo under the input. Every field looks the same whatever its label's length.

F2 As now, fixed only where it breaks

Keep full-width inputs and the badge beside the label; only stop the unit from wrapping. Smaller change, but badges still move and inputs with a unit stay narrower.

Recommendation: N1, with G2 and F1

N1 fixes every item in the issue with the least new structure, keeps the edit screen as fast to change as it is now, and follows the plainest guidance on form layout. G2 puts the beam's size and its species together, which is how you shop for it and how the checks use it. F1 makes every field the same shape, so the column reads evenly at every width.

Built as: the generic form groups in core with the template's own grouping in its folder; Sidebar with a sticky side (a new option, catalog and tests), a progress line counting entered and input-needed fields, Create in the side and the header; Field laid out as F1. Checked at 320, 375, tablet, and laptop widths, light and dark.

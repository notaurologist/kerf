Kerf · Design milestone · Issue #45

Design system

Stages 0 to 5b decided what Kerf looks like and says. This stage builds it in code: tokens, layout primitives, components, and a catalog page, and then rebuilds every M4 screen from them. What the system contains is already decided; the inventory below maps each piece to the stage that decided it.

What is open is how it is built: where the code lives, how styles are written so screens cannot add one-off styles, and how the work lands. Today the web app has one 517-line stylesheet with the system font and a brown accent, and none of the stages applied.

Decided, October 2026

The owner took the suggestion for all four: DS1, in apps/web, four PRs, no new dependencies. The build is #78 (foundations), #79 (components and catalog), #80 (screens), and #81 (guidance). Reasons and rejected directions are in docs/design/README.md. The choices were:

  1. How styles are written: DS1 layered global CSS, DS2 CSS Modules, or DS3 tokens in TypeScript.
  2. Where it lives: apps/web/src/ui, or its own package, packages/ui.
  3. How it lands: four pull requests under sub-issues, or one.
  4. Test dependencies: none for now, an accessibility checker, or screenshot tests.

Directions

Three ways to write the styles

Each shows the same component, a length field with its echo and error, and how the editor uses it. None needs a new dependency. In all three, screens are built only from components and layout primitives; the difference is how that is enforced and where each rule lives.

DS1 · Layered global CSS · Chosen

Tokens and layout primitives as global CSS in cascade layers, component blocks with a k- prefix, states as data attributes

From the subject
CUBE CSS and Every Layout: work with the cascade rather than against it, compose pages from a few global layout primitives, and keep component ("block") styles small. #41 already chose those primitives (Stack, Sidebar, Switcher, Cluster, Center), which are global by nature. Cascade layers (@layer, in every current browser since March 2022) fix the order of reset, tokens, base, layout, components, and print, so specificity never decides which rule wins.
Principles
One stylesheet per concern, in a fixed order. Tokens are custom properties, so shop density and dark mode are a change of tokens on a container, not new rules. Print rules sit in one layer, which suits #41's section-order print.
In use
Screens never write styles: a test fails if any file outside ui/ passes className or style. Components set states with data attributes (data-state="error"), which the catalog page can show one by one.
Cost
Class names share one namespace, so blocks carry a k- prefix. No tooling to add: Vite bundles plain CSS, and render tests see the real class names.

DS2 · CSS Modules

Each component's styles in its own module, renamed at build so nothing outside can reach them

From the subject
Component-scoped styles, as many React design systems write them: each component has a .module.css file beside it, and the build renames its classes so nothing outside can reach them. Vite treats any *.module.css file this way with no extra install.
Principles
The no-one-off-styles rule is built in, since a screen cannot target a component's classes. Each component's styles, including its print rules, live next to it.
In use
Layout primitives and tokens still need a global stylesheet, so there are two kinds of CSS. Print rules for the whole plan (section order, page breaks) are spread across modules. Vitest skips CSS Modules by default and returns placeholder class names, so render tests need it switched on to check states by class.
Cost
One more convention and a test-config change. No dependency.

DS3 · Tokens in TypeScript

One TypeScript token file for everything, written out as CSS variables, applied through typed style props

From the subject
Tokens as TypeScript, the single source for everything: a small build script writes them out as CSS custom properties, the contrast test reads them directly, and components apply them through typed style props. The Design Tokens Community Group's format (first stable version 2025.10) is the standard shape for such a file.
Principles
The type checker catches a misspelled token, and the diagrams' SVG, the screens, and the test share one file.
In use
Inline styles cannot express hover, focus, container queries, or print, which Kerf needs everywhere (#41's components respond to their own width, and the plan prints). Those would still need CSS, so there would be two systems. It is half of a CSS-in-JS library, written by hand.
Cost
A build step, a generated file to keep in sync, and the most code to maintain.

Where it lives

A folder or a package

apps/web/src/uiSuggested

Tokens, primitives, components, and icons in one folder of the only app that uses them. Screens import from ui/; nothing in ui/ imports a screen. The review pages in docs/design/ stay standalone HTML.

packages/ui

Its own workspace package, as if a second app might use it. A package boundary, build, and version for one consumer; worth it only if a second app is planned, and none is.

How it lands

Four pull requests, or one

AGENTS.md asks for small, focused changes. #45 touches every screen, so one pull request would be the largest in the project and the hardest to review on a phone.

Four pull requestsSuggested

Each a sub-issue of #45, in order:

  1. Foundations: self-hosted fonts, tokens, base styles and layers, layout primitives, the contrast test.
  2. Components and catalog: every component above with its states, icons, the catalog page, and accessibility tests.
  3. Screens: login, projects, tools, the editor (#67's states, #68's strings), and the plan (cut list, shopping list, structural review), with the old stylesheet removed.
  4. Guidance: usage guidance in docs/design/, ARCHITECTURE.md, and the check against #45's "Done when". Then #69, the garage check.

Each leaves the app working and is checked in a Vercel preview.

One pull request

Everything at once. Nothing is half-switched at any point, but the review is long and a problem found late holds up all of it.

Test dependencies

What checks the system

Without new dependencies, the system is checked by: the contrast test (WCAG's formula, written in the repo), render tests of each component's states and accessible names, a test that screens pass no className or style, the catalog page, and the garage check (#69).

None for nowSuggested

Start with the checks above. Revisit after the garage check, when it is clearer what slips through.

An accessibility checker

An automated rule checker run against each rendered component in the tests. Catches missing labels and roles; needs a browser-like test environment, so two development dependencies.

Screenshot tests

A headless browser takes pictures of the catalog and key screens and compares them with stored ones. Catches visual drift; one large development dependency and stored images to update with every intended change.
